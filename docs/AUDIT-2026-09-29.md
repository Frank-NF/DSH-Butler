## 0. 一页结论

**综合风险等级：中高（Medium-High）。共 19 条问题 —— 高危 2 / 中危 9 / 低危 8。**

安全基线明显高于同类桌面工具：Host 白名单挡 DNS rebinding、cmd.exe 元字符闸口、搬移包路径穿越双重校验、
写前回滚点 + 事务日志 + 域级互斥锁，这些都是很多团队懒得做的。

真正的隐患类型是同一句话：**「规矩写在注释里，实现没跟上」**。
最典型的是 `server.ts:452` 白纸黑字写着「密钥 GET 永远只给掩码」，`453-462` 也确实只给掩码；
但同一个文件的 `/api/settings`（`:567`）把整个 `AppConfig` 连 `ai.apiKey` 明文一起吐了出去 —— 两套口径自相矛盾。

最要紧的三件事：

1. **SEC-20（高危）** 📄 —— `/api/settings` GET 返回 AI 密钥**明文**。与「令牌长期挂在 URL 上」叠加后，
   令牌泄漏的后果从「能操控管家」升级成「能盗刷用户 API 额度」。
2. **SEC-21（高危）** 📄 —— 会话令牌长期挂在 `?t=` 上（历史、会话恢复、进程命令行），
   而 cookie 通道早已建好，query 通道**没有随之退役**。
3. **SEC-22（中危）** 📄 —— 日志只在**导出**时脱敏，`util/log.ts` 落盘前不脱敏。
   而 `domains/runtime/dsh-url.ts` 恰恰证明了日志里确实躺着 DSH 令牌。

**做对的地方**：依赖面极小（仅 `jsr:@std/assert@1.0.19`，`deno.lock` 已入库且带 integrity）、
`config.ts` 的配置损坏留证不静默清零、搬移包 `resolveTarget` 双重校验、`engine.ts` 的写前落盘与补偿动作逆序执行。

## 2. 高危问题

### SEC-20 · 高危 · `/api/settings` 把 AI 密钥明文吐回前端 📄

- **位置**：`src/api/server.ts:563-584`，关键行 `567`（`config: cfg`）；同源问题见 `:689`（`saveConfig({})` 的返回值）
- **对照**：同文件 `src/api/server.ts:452` 注释「GET 永远只给掩码」，`453-462` 只返回 `keyMasked`。
  但 `/api/settings` 直接序列化整个 `AppConfig`（`domains/state/config.ts:87` 的 `ai: AiConfig`，含 `apiKey: string`）
- **影响**：任何能过本机认证的调用方都能拿到 **OpenAI 兼容接口的明文密钥** —— 拿到 token 的本机其它进程、
  DNS rebinding 后的同源会话、webview 里加载的第三方页面脚本。用户填的是付费 API key，且会进入浏览器内存与抓包工具
- **与 SEC-21 的叠加**：SEC-21 让令牌更容易泄漏，SEC-20 让泄漏后果从「能操作本机」升级为「能花钱」
- **修复方向**：GET 分支改用 `configSummary()`（`config.ts:296` 已写好，只是没人用），
  或至少把 `ai` 换成 `{ baseUrl, model, attachDiagnostics, hasKey, keyMasked }` —— 与 `/api/ai/config` 保持**同一形状**；
  并补一条测试钉死「设置接口响应体里不得出现 `apiKey` 字段」

### SEC-21 · 高危 · 会话令牌长期挂在 URL 上（`?t=`） 📄

- **位置**：`src/api/server.ts:193`（接受 query 令牌）；`:986-994`（`withSessionCookie` 依赖 `/?t=<令牌>` 完成首次发牌）；
  `main.ts:210`（把带令牌的 `appUrl` 交给 `openBrowser`）
- **影响**：令牌进入浏览器历史、webview 会话恢复数据、以及 `deno desktop` 的**进程命令行参数**
  （本机任意用户 `tasklist` / 读 `/proc` 即可看到）。令牌是进程级长效的，泄漏即长期有效。
  注释 `:103-113` 自己承认这是「EventSource 无法设请求头」的妥协 —— 但 cookie 通道建好后，**query 通道没有退役**
- **修复方向**：cookie 兑换成功后立即 `history.replaceState` 抹掉 URL 里的 `t`；
  或改为「一次性兑换码」——`?t=` 仅用于换 cookie，换完即失效，后续只认 cookie 与 header

## 5. 待验证项与缺失上下文（不做臆断）

以下各条**未下结论**，需补充信息或实测才能判定：

1. **SEC-23 标注为「疑似」** 🔍 —— 依据是 WHATWG Streams 规范中 `controller.close()` 不触发 `cancel()` 回调。
   但 Deno 的 HTTP 服务器在响应结束后是否额外调用 `cancel()` 属运行时实现细节，静态阅读无法确认。
   建议实测：连续创建 20 个任务，观察定时器与监听器数量是否累积。
2. **SEC-24 的 `--no-sandbox` 是否必需** —— `.env` 注释称是本�� Chromium 沙箱初始化失败（`0x80000003`）的兜底。
   若属普遍现象则风险可接受；若只是个例则不该随包分发。需确认受影响范围。
3. **`scripts/` 的 ed25519 验签是否仍在使用** —— `key-info.json` 保留公钥与三次轮换历史，
   但 `src/` 中**未找到任何 ed25519 验签代码**（只有 sha256 用于备份校验）。
   若已废弃，`key-info.json` 与拦截钩子应一并清理；若仍在使用，需确认验签发生在哪一侧（可能是 DSH 本体而非管家）。
4. **市场目录投毒的影响面未完整评估** —— `net/market.ts` 未逐行读完。已沿渲染（已转义）与安装（过 cmd 闸口）
   两条路径做局部推断，未做完整评估。
5. **`.env` 是否随包分发** —— 已被 `.gitignore` 正确忽略，但若打包流程会把它打进 exe 同级目录，
   `--no-sandbox` 就会变成对所有用户的默认行为。需核对 `scripts/` 下的打包脚本。
