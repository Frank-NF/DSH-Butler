# DSH管家 功能路线图建议（2026-09-25）

> 背景：官方桌面预览版已经出来了。这份建议的前提是**先把官方到底做了什么查清楚**，再决定我们不该做什么、该做什么。
> 事实来源两类：① 本机检出 `G:\DeepSeek_Harness\apps\desktop`（v0.1.7-rc.2，官方桌面端源码）；② 本项目此前的调研 `docs/research-official-desktop.md`（含线上实测）。

---

## 0. 一句话结论

**别再往「壳」上投入了 —— 官方已经把窗口、托盘、单实例、安装器、自动更新、首次引导都做完了。**

管家的下一个身份应该是 **DSH 的「运维台 ＋ 急救箱」**：官方负责「把 DSH 跑起来」，我们负责「把它跑得稳、出事能修、换机能搬、版本能退、依赖能治」。
这块官方**结构性地不会做** —— 它的目标是让自家应用永远不需要你打开第二个工具。

---

## 1. 官方桌面端已经覆盖了什么（有据可查）

从 `apps/desktop/src/` 的文件名就能读出来（这些不是猜的）：

| 能力 | 官方实现（证据文件） | 我们的对应物 |
| --- | --- | --- |
| 窗口壳 / 内嵌 Web | `main.ts`、`host-process.ts`、`host-protocol.ts` | 我们的 deno-desktop 壳 |
| **托盘** | `tray.ts`、`render:tray-icon` | `host/desktop.ts` 自绘托盘 |
| **单实例保护** | `single-instance.ts` | 今晚刚补的 `host/single-instance.ts` |
| **自动更新（含强制更新策略）** | `mandatory-update-policy.ts`、`mandatory-update-window.ts`、`update-attention.ts`、`preload-update-dialog.ts` | `net/butler-update.ts`（只提示、不自动） |
| **安装器 / 卸载器 / 卸载清数据** | `installer/*.nsh`、`uninstall-data.h`、`lifecycle.nsh` | 无（只有便携 exe） |
| **首次引导** | `lib/welcome/`、`preload-welcome.ts` | 我们的 onboarding 提示 |
| **崩溃上报 / 启动失败兜底** | `crash-report.ts`、`fatal-recovery.ts`、`startup-error.ts` | 无 |
| 多语言 / 主题 / 快捷键 | `locale.ts`、`preload-theme.ts`、`keybindings.ts` | 中英未做，主题与快捷键已有 |
| **插件管理（内置 pnpm，不依赖 PATH）** | README.zh.md 原话：Creator 与 Web Plugin Manager 用 Desktop 内置 pnpm | 我们的插件市场（走系统 npm） |
| 平台账号内嵌文档 / 项目管理 / 目录选择 | `platform-view.ts`、`project-manager.ts`、`directory-picker.ts` | 无 |
| 退出确认 / 后台通知 / 麦克风权限 | `quit-confirmation.ts`、`background-notice.ts`、`microphone-permissions.ts` | 无 |

外加事实（来自线上调研）：官方桌面端**只有 nightly 通道、只有 Windows 公开包、官网还没有下载入口**，自称「开发者预览」；
而它把 Electron 壳与 dsh 运行时**锁死为同一版本、整体更新**（`core-package-set.ts`、`runtime-tree.ts`），CLI 侧**连 `update` 命令都没有**。

### 1.1 顺带一个不太好的消息

DSH **Web 应用自己**已经把插件市场、已安装/可更新/发现、技能中心开关做进设置页了（界面实测：`插件市场 / 发现 / 主题 / 收藏 / 已安装(14) / 更新 / 卸载`）。
**我们的插件市场在浏览体验上很难长期赢过它** —— 它是第一方，能直接读自己的注册表。所以「商店」不该是我们的主战场。

---

## 2. 因此：不要再投入的方向（反清单）

1. **壳的体验**：窗口尺寸/位置、无边框、圆角、动画 —— 官方 Electron 壳是原生级，追不上也不该追。
2. **安装包与卸载器**：NSIS/MSI、开始菜单、卸载清数据 —— 官方有完整实现（含 `uninstall-data.h`）。
3. **自动替换自己**：我们已在 `UPDATE-STRATEGY.md` 里论证过不做；官方甚至做了强制更新策略，这块更没意义。
4. **插件商店的浏览/搜索/分类**：官方 Web 第一方体验更好；我们保留「够用、能触发运维动作」即可。
5. **首屏引导、崩溃上报**：官方已有 `welcome` 与 `crash-report`。

一句话：**凡是「官方桌面端多写一页就追上」的功能，都不要投。**

---

## 3. 该做的：P0 / P1 / P2

### P0 —— 差异化核心（建议下一批就做，1-2 周）

#### P0-1　体检升级为「体检 ＋ 一键修」（Doctor with Fix）
- **做什么**：现有体检只报不修。每条问题配一个可执行的处置动作，且处置前自动建回滚点、处置后自动复检。
  首批覆盖：端口被占（含今天踩到的 Windows 保留端口区间）、profile 的 package.json 损坏、依赖锁冲突、
  残留目录、写锁残留、配置损坏（今晚加的「留证再回退」正好接上）、Node/npm/pnpm/git 缺失。
- **为什么官方不做**：官方只负责自家应用能不能起来；**「你的环境坏了」不是它的职责**，它一旦动手修用户环境就要背责任。
- **落地**：`domains/diag/health.ts` 已有体检内核 → 给每条 finding 补 `fixAction`（这个机制已经存在）、
  新增 4-6 个 repair 动作（已有部分：`runtime.repair`、`plugin.cleanResidue`、`core.deepClean`）。**工作量：中**。

#### P0-2　错误翻译器（把 npm/pnpm/git 报错翻成人话 ＋ 一键处置）
- **做什么**：把常见 15-20 类原始报错映射成「人话成因 ＋ 影响 ＋ 一键动作」。
  今晚那次 `ERESOLVE` 就是最好的模板：用户看到几十行 npm 堆栈，真实原因只有一句「两个插件要的 peer 版本不一样」。
  其它高频：`EACCES`（文件被占）、`ETIMEDOUT`/`ECONNRESET`（网络或镜像）、`404`（包名错或镜像没同步）、
  `ENOSPC`（磁盘满）、`EPERM`（杀软/权限）、`EBUSY`（进程占着文件）。
- **为什么官方不做**：它的内置 pnpm 只要成功就行；**报错解释是运维工具的活**。
- **落地**：新增 `src/util/error-translate.ts`（纯函数 ＋ 测试），在安装/更新失败的结果页展示。**工作量：小**。

#### P0-3　依赖冲突可视化 ＋ 锁文件修复
- **做什么**：解析 profile 依赖树，画出「谁要的版本和谁不一致」，并给可执行建议（升级/降级/共存/改宽松解析）；
  顺带修锁文件：`package-lock.json` 与清单不一致时一键重建。
- **为什么官方不做**：插件生态的依赖冲突是**第三方插件的锅**，官方没动力替它们擦。
- **落地**：已有 `net/npm-registry.ts` 与 profile 清单读取；需新增依赖树解析（`npm ls --json`）。**工作量：中**。

#### P0-4　回滚点时间线（可视化 ＋ 一键回退 ＋ 影响预览）
- **做什么**：把回滚点从列表升级为时间线：谁在何时改了什么、影响哪些文件/插件、能否一键回到那时，并给出回退影响预览。
- **为什么官方不做**：官方强制整体更新，没有「回到某个中间状态」的概念。
- **落地**：`domains/backup/rollback.ts`、`domains/core/rollback.ts` 已实现文件级逆操作；主要是界面与预览。**工作量：中**。
### P1 —— 运营价值（2-4 周）

#### P1-1　多 profile / 多实例管理台
- 官方桌面端是**一个应用一个 profile runner**；DSH 自身有 `web`/`desktop`/`sdk`/`headless` 多个 profile。
- 我们做：每个 profile 独立启停、端口分配与冲突排查、插件清单各自可见、一键切换。**为什么官方不做：它只跑自己那一个。工作量：中**。

#### P1-2　数据搬家与定时备份（换机迁移向导）
- 一键导出/导入：`~/.dsh` 下的配置、profile 清单、技能、会话（可选）、以及 `~/.dsh-butler` 的回滚点索引。
- **为什么官方不做**：官方把数据当自己应用的内部状态，不做跨机迁移。**工作量：中**。

#### P1-3　插件批量运维 ＋ 更新前后验证
- 已有批量安装/更新雏形（市场勾选）。补：更新前自动回滚点 → 更新后**验证 DSH 能否正常启动**（跑一次体检）→ 失败自动回退并给出原因。
- 这正是「管家」相对「商店」的核心价值。**为什么官方不做：官方只更新自家运行时，不逐个验证第三方插件。工作量：中**。

#### P1-4　离线 / 内网 / 镜像（把今晚修好的设置做深）
- 今晚刚把「npm 安装源 / 网络代理」真正接进 npm。继续做：镜像测速与自动选择、离线包（tgz）拖进来安装、企业配置一键导入导出。
- **为什么官方不做**：它面向公开网络的分发通道。**工作量：小-中**。

#### P1-5　DSH 本体多版本并存与切换
- 同时保留两个本体（`next` / `latest` / 指定 tag），一键切换与回退；并能解释「npm 的 latest 落后于 next」这类陷阱
  （我们调研里实测过：latest=0.1.5-rc.3 反而比 next=0.1.7-rc.2 旧）。
- **为什么官方不做**：它把壳与运行时锁死为一个版本、只能整体更新。**工作量：中-大**（要处理目录切换与进程锁）。

### P2 —— 体验与生态（1-2 个月）

| 编号 | 建议 | 一句话理由 |
| --- | --- | --- |
| P2-1 | 技能与配置 Git 化（把 `~/.dsh/skills` 与关键配置纳入版本控制，可回退可同步） | 官方不管你的技能资产；与已装的技能中枢天然互补 |
| P2-2 | 一键导出「可分享的诊断包」（脱敏后的日志＋体检＋依赖树） | 求助/提 issue 时最省事，也体现专业度 |
| P2-3 | 定时任务：定时体检、定时查更新、异常托盘提醒 | 已有保活定时器与托盘，扩展成本低 |
| P2-4 | 写操作审计报告（谁在何时改了什么，可导出） | 已有事务日志与回滚点做底座，面向企业/多人场景 |
| P2-5 | 与官方桌面端共存策略：检测到官方桌面端时自动降级为「运维/急救」模式 | 不抢壳、明确分工，反而更受欢迎 |

## 4. 定位建议（一句话版本）

> **官方桌面端：把 DSH 跑起来。管家：让 DSH 一直能用。**

| 用户场景 | 谁来接 |
| --- | --- |
| 第一次装 DSH、想要个窗口 | **官方桌面端**（我们不再抢） |
| 浏览插件、点一下装 | **DSH Web 的插件页**（第一方体验更好；我们保留入口用于批量/运维） |
| 「装完起不来了」「插件冲突了」「端口被占了」「配置坏了」 | **管家**（体检＋一键修＋错误翻译） |
| 「升级后想退回去」「换电脑要搬走」 | **管家**（回滚时间线＋数据搬家） |
| 「内网不能直连 npm」「要同时开 web 与 desktop 两个 profile」 | **管家**（镜像/代理/离线 ＋ 多 profile 台） |
| 「官方桌面端起不来」 | **管家**（便携、不依赖安装器，能当急救工具） |

## 5. 如果只做一件事

**做 P0-2（错误翻译器）。** 理由：纯函数、零风险、当天可交付，而且**今晚刚刚发生了一次真实的 ERESOLVE** ——
用户看到的是几十行 npm 堆栈，真实原因只有一句「两个插件要的 peer 版本对不上」。
把这 15-20 类错误翻成人话并给出按钮，是「管家」这个身份最直接、最容易被感知的价值。

接下来按性价比排序：**P0-2 → P0-1 → P0-4 → P0-3 → P1-3**。
