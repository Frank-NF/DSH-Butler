# DSH 增强外壳 · 改版升级开发方案（Deno 2）

> 文档版本：v1.0 · 2026-09-24
> 目标基线：现有 `DSH插件管家` 1.18.15（Tauri 2 + Vue3）→ 全新 `DSH 增强外壳`（Deno 2.9 + deno desktop + Vue3）
> 适用范围：本机自用 + 后续对外分发
> 本方案中所有 Deno 能力结论均基于 **本机实测 Deno 2.9.7** 与官方文档（2026-06/07 更新）核实，非推测。

---

## 0. 一页纸结论（先看这段）

| 问题 | 结论 |
|---|---|
| 技术栈能不能成立？ | **能。** 本机已装 `deno 2.9.7 (stable, x86_64-pc-windows-msvc)`；`deno desktop` 自 2.9.0 起可用，能直接产出 Windows `.msi`／macOS `.app`／Linux `.deb/.AppImage`，一次开发三平台出包，不再需要 Rust 工具链 |
| 是"命令透传壳"吗？ | **不是。** 核心是一个**领域服务层 + 任务引擎**：所有操作以「任务（Job）」为单位，带步骤、进度、取消、审计、崩溃恢复、回滚点。UI 和 CLI 都只是它的两个消费者 |
| 最大的技术风险 | **`Deno.autoUpdate()` 在 Windows 上目前不生效**（官方原文：patches 会下载并暂存，但 launcher 不会换入，*"Treat Windows auto-update as not yet supported"*）。→ 管家自更新必须自研，沿用现有"下载新 exe + 外部替换 + 重启"方案 |
| 第二个风险 | `deno desktop` 在 2.9 是 **experimental**。对策：锁定 Deno 版本 + 能力抽象层 + 保留 1.18.x 回退 + 每版回归清单 |
| 现有代码的处置 | **Rust 15 个模块 70% 的逻辑价值要移植，30% 的框架代码直接丢弃**。真正的资产是「疑难杂症的处理知识」（隔离区、僵尸锁、构建重试、事务安装），不是 Tauri 那层壳 |
| 建议的发布节奏 | 先发 `2.0.0-alpha`（只读诊断，绝不碰用户数据）→ 再逐步接管写操作。**不要一次性把 1.18.15 替换掉** |

## 2. 技术选型

### 2.1 结论

```
Deno 2.9.x（锁定小版本）
  ├─ deno desktop   → 桌面窗口（webview 后端，非 CEF）
  ├─ Deno.serve     → 本地 HTTP API + SSE 事件流 + 静态托管前端
  ├─ Deno.Command   → 所有子进程（git / pnpm / node / 系统命令）
  ├─ Deno.KV        → 状态库（SQLite 后端）：任务历史、回滚点、探测缓存
  ├─ WebCrypto      → SHA-256 / Ed25519 验签（复用现有签名体系）
  ├─ Deno.BrowserWindow / Deno.Tray → 原生窗口、托盘、菜单、原生对话框
  └─ 前端保留 Vue3 + Vite（不重写）
```

### 2.2 为什么是「Deno + deno desktop」而不是「继续 Tauri」或「纯 Node/Electron」

| 维度 | Tauri 2（现状） | Electron | **Deno 2.9 + deno desktop** |
|---|---|---|---|
| 跨平台成本 | 高：Cargo.toml 里 reqwest/tokio/sysinfo/winreg/keyring 全被 `cfg(windows)` 包住，**非 Windows 根本编译不了** | 中 | 低：一套 TS，`--target` 直接交叉编译 |
| 产物体积 | 裸 exe ≈ 19.7 MB（现状） | 100 MB+ | webview 后端 66 MB，`--compress` 后 **≈19 MB** |
| 打包 | NSIS 能用，MSI 需手工改 wxl/wxs 绕 LGHT0311 | 简单 | `.msi` 一行参数直出（纯 Rust 实现，任意宿主可交叉编） |
| 系统运维能力 | 需 Rust 生态（强） | 需 Node 生态 | Deno.Command + 系统命令 + FFI（够用，见 §11 风险） |
| 自更新 | 自研（现状已跑通） | 成熟 | **Windows 上 Deno.autoUpdate 不可用** → 仍需自研，**无收益也无损失** |
| 生态风险 | 稳定 | 稳定 | ⚠️ `deno desktop` 2.9 起 experimental |

**决策理由（业务语言）**：现有 Rust 那 70 条命令里，真正值钱的是"怎么修"的经验知识，不是 Rust 本身。跨平台是这次改版绕不开的需求，而 Tauri 现状是**结构性锁死在 Windows**——继续在 Rust 上加平台，等于把每个模块都重写一遍还要维护三套条件编译。换 Deno 是**一次性的移植成本**换**长期的单一代码库**。

### 2.3 硬约束（必须提前接受，不能装看不见）

1. **`Deno.autoUpdate()` 在 Windows 无效**
   官方明确：patch 能下载、能暂存，但 Windows 上 launcher 不换入（加载中的 DLL 不能就地替换）。
   → **自更新模块必须自研**：下载完整新包 → SHA256 校验 → Ed25519 验签 → 写 `.new` → 启动 detached 替换脚本 → 重启。现有 `self_update` 的逻辑可以整段移植。Ed25519 签名的用法可对齐官方 manifest 的 `{signed, signature}` 信封格式，**一套密钥两用**。

2. **权限在编译期烘焙进二进制**
   `deno desktop` 的权限等于 `deno run` 的权限，编译时给的权限就固化在产物里。
   → 本工具本质是**系统运维工具**（要读写任意盘、跑子进程、访问网络），**必须宽授权**。
   → 因此 Deno 的默认安全模型在这里**不构成安全边界**。安全必须靠另一套机制补（见 §9.6）。

3. **macOS `.dmg` 必须在 macOS 上构建**（要 shell 调 `hdiutil`）。
   → 其他格式（`.app` / `.msi` / `.deb` / `.rpm` / `.AppImage`）都能在 Windows 上交叉编。若你没有 Mac，第一期不做 `.dmg`。

4. **编译后 `Deno.cwd()` 是用户的 cwd，不是 exe 所在目录**。
   → 所有自身资源（前端产物、规则库、图标）必须走嵌入虚拟文件系统，**不能靠相对路径猜**。

5. **纯 Vite SPA 不在 `deno desktop` 的框架自动检测列表里**（列表是 Next/Astro/Fresh/Remix/React Router/Nuxt/SvelteKit/SolidStart/TanStack Start/Vite SSR）。
   → 我们的前端是静态 SPA，**需要自己写入口**：`deno desktop` 指向自写的 `main.ts`，在里面 `Deno.serve()` 托管 `dist/` 静态文件。这不是问题，但要写对，别指望自动检测。

## 3. 总体架构

### 3.1 分层

```
┌──────────────────────────────────────────────────────────────────┐
│  L4  UI 层（webview 内运行）                                       │
│  Vue3 SPA：总览仪表盘 / 本体 / 插件 / 运行 / 环境 / 一键部署 / 日志   │
│  通信：fetch → REST API ；订阅：EventSource → SSE 事件流             │
│  原生能力（窗口/托盘/原生对话框）：window 原生绑定，仅此一处直连        │
└───────────────┬──────────────────────────────────────────────────┘
                │ http://127.0.0.1:<动态端口>   ← 同进程内网，不对外暴露
┌───────────────▼──────────────────────────────────────────────────┐
│  L3  接口层  Interface Layer                                      │
│  HTTP Router  ·  SSE Hub  ·  CLI Router（--headless）             │
│  职责：鉴权（本地 token）、参数校验、Job 创建、事件广播               │
└───────────────┬──────────────────────────────────────────────────┘
┌───────────────▼──────────────────────────────────────────────────┐
│  L2  编排层  Job Engine + Policy                                  │
│  Job 状态机 · 步骤表 · 超时/取消 · 补偿动作 · 回滚点 · 审计写入       │
│  崩溃恢复（jobs/*.json）· 幂等判定 · 权限预检 · 冲突互斥锁            │
└───────────────┬──────────────────────────────────────────────────┘
┌───────────────▼──────────────────────────────────────────────────┐
│  L1  领域层  Domain Services（12 个模块，见 §5）                    │
│  core / plugin / runtime / env / bootstrap / self / backup /       │
│  market / network / diagnose(规则库) / state / audit              │
└───────────────┬──────────────────────────────────────────────────┘
┌───────────────▼──────────────────────────────────────────────────┐
│  L0  主机适配层  Host Adapter（跨平台收敛点，唯一碰 OS 的地方）       │
│  process · port · fs(原子/隔离) · privileges · env · registry ·    │
│  pkg-manager · shell · path                                        │
│  ┌─ windows.ts ──┬─ macos.ts ──┬─ linux.ts ─┐                     │
└──────────────────────────────────────────────────────────────────┘
```

**设计要点**：
- **L0 是唯一允许出现 `if (Deno.build.os === 'windows')` 的地方**。业务模块永远不提平台。
- **L3 有一个隐藏收益**：HTTP API 是标准协议，所以这套东西天然支持"浏览器打开本机端口做远程运维"（比如以后从服务器上的 DSH 做同样的诊断）。UI 不是唯一入口。

### 3.2 数据流

**写操作（以"更新本体"为例）**

```
用户点“更新 DSH 本体”
  → UI: POST /api/jobs  { action:"core.update", params:{...} }
  → L3: 校验 action 白名单 + 本地 token + 参数 schema
  → L2: 权限预检(磁盘可写/进程可停) → 冲突锁检查(是否有其它 Job 在改本体)
         → 创建 Job{ id, action, 步骤表[6 步], 超时表, 补偿动作表 }
         → 先落盘 jobs/<id>.json（write-ahead）→ 返回 job_id（<100ms）
  → UI: new EventSource('/api/jobs/<id>/events')
  → L2 后台执行：第 0 步先建回滚点（记录 git HEAD + 关键文件哈希）
                逐步调用 L1 → L0 → 系统
                每步: emit step-start / step-log / step-done | step-failed
  → 任一步失败: 执行该步的补偿动作 → Job 置 failed → 附带现场(日志摘录 + 诊断建议)
  → 全部成功: 写审计 → 触发 postVerify(core.verify) → Job 置 succeeded
```

**读操作（状态/体检）**

```
UI: POST /api/jobs { action:"diag.healthCheck" }（同样的 Job 通道，保证可审计）
或 UI: GET /api/state/overview（只读快照，走缓存，不建 Job，用于首屏秒开）
```

**关键约定**：
- 所有**有副作用**的操作必须走 Job 通道；所有**纯读**可以走 `/api/state/*` 快速通道（带 500ms~5s 缓存）。
- 所有 Job 事件同时写入审计流，UI 刷新后可回放（`GET /api/jobs?limit=50`）。

### 3.3 前端保留策略

| 保留 | 说明 |
|---|---|
| Vue3 + Vite + 25 个组件 | 直接复用，仅把 `invoke('cmd', args)` 改成 `callAction('cmd', args)`（一个适配器文件搞定） |
| i18n zh/en | 保留，新增文案按需补 |
| 主题系统 v4.1（橙红主色 / 明暗） | 保留，`useTheme` 不动 |
| 自研 W* 组件族（WButton/WDialog/WToast/WSheet…） | 保留，这些是资产 |
| 图标系统 v4.0 蓝紫盾牌 | 保留，`.ico` 直接喂给 `deno.json` 的 `app.icons.windows` |

**要改的**：`src/api/index.ts`（Tauri invoke → HTTP）、`AutoUpdateFloat.vue`（改接新的自更新 Job）、新增 5 个页面组件（总览/日志/环境/一键部署/回滚）。

## 4. 命令与子命令设计

### 4.1 命名空间（12 个动作域）

| 命名空间 | 职责 | 动作示例 |
|---|---|---|

| `runtime.*` | 运行态管理 | `status` `start` `stop` `restart` `health` `logs` **`diagnose`** **`repair`** |
| `env.*` | 环境与配置 | `probe` `ports` `paths` `perms` `deps` `wizard` |
| `bootstrap.*` | 一键部署 | `plan` `apply` `verify` |
| `self.*` | 管家自身 | `version` `check` `update` `rollback` `settings` |
| `backup.*` | 备份点（统一回滚点） | `list` `create` `apply` `delete` `verify` |
| `market.*` | 插件市场 / 目录 | `catalog` `bundle` `preview` `install` |
| `network.*` | 网络与镜像 | `probe` `proxy` `mirror` |
| `mcp.*` | MCP 配置 | `list` `saveEnv` `apply` `probe` `toggle` |

### 4.2 REST API（L3）

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/state/overview` | 首屏快照（本体/服务/插件计数/环境摘要），带缓存 |
| `GET` | `/api/state/:domain` | 各域只读快照（`/api/state/env` 等） |
| `POST` | `/api/jobs` | 创建任务 `{ action, params, confirm }` → `{ jobId }` |
| `GET` | `/api/jobs/:id` | 任务当前状态 + 步骤表 |
| `GET` | `/api/jobs/:id/events` | **SSE**：步骤进度、日志行、心跳 |
| `POST` | `/api/jobs/:id/cancel` | 请求取消（触发补偿动作） |
| `GET` | `/api/jobs?limit=&domain=` | 历史任务 |
| `GET` | `/api/events` | 全局事件流（服务状态变化、插件变更、外部文件变动） |
| `GET` | `/api/logs/tail?source=&n=` | 日志 tail（`source`: butler / dsh-startup / dsh-runtime） |
| `GET` | `/api/logs/search?q=&from=&to=` | 日志检索（倒排索引缓存） |
| `POST` | `/api/diag/export` | 导出体检报告（脱敏后 JSON/Markdown） |
| `GET` | `/healthz` | 容器级存活探针 |

**安全**：本地 token（启动时生成，注入 webview 的 `window.__BUTLER_TOKEN__`），所有非 `/healthz` 请求校验 `X-Butler-Token`；端口随机绑定 `127.0.0.1`（不监听 0.0.0.0）。

### 4.3 CLI（同一核心层的第二个消费者）

```bash
# GUI（默认，无参数）
dsh-butler

# 只读诊断（绝无副作用，可安全地在任何机器上跑）
dsh-butler doctor                       # 全量体检
dsh-butler doctor --json -o report.json # 机器可读
dsh-butler env probe [--json]
dsh-butler env ports [--json]
dsh-butler core status [--json]
dsh-butler plugin list [--json] [--outdated]
dsh-butler runtime status|health|logs [-f] [--lines 200]

# 诊断（只读，给出结论与建议）
dsh-butler plugin diagnose [<id>]
dsh-butler runtime diagnose
dsh-butler diag rules                    # 列出诊断规则库

# 写操作（--yes 非交互；无 --yes 时打印计划并要求确认）
dsh-butler core update        [--yes] [--mirror <url>]
dsh-butler core finishUpdate  [--yes]
dsh-butler core rollback      [--to <rollbackPointId>] [--yes]
dsh-butler core verify
dsh-butler plugin install <id> [--yes]
dsh-butler plugin repair <id>   [--yes]

# 一键部署
dsh-butler bootstrap plan                # 只输出计划，不做任何事
dsh-butler bootstrap apply [--yes]
dsh-butler bootstrap verify

# 任务
dsh-butler job ls [--limit 20]
dsh-butler job show <id>
dsh-butler job cancel <id>
dsh-butler job log <id>

# 自身
dsh-butler self check|update|rollback
```

**约定**：
- 所有子命令支持 `--json`（stdout 只输出 JSON，日志走 stderr）→ 便于将来接 CI / 服务器 / 自动化。
- 所有写操作遵循 **plan → confirm → apply** 三段式。`plan` 永远无副作用。
- 退出码语义固定：`0` 成功 / `1` 一般失败 / `2` 参数错误 / `3` 权限不足 / `4` 前置条件不满足 / `5` 超时 / `6` 取消。

## 7. 配置与状态存储

### 7.1 目录布局（新根目录，不污染 `~/.dsh`）

```
~/.dsh-butler/                    ← 管家自己的家，可整体删除不影响 DSH
├── config.json                   用户配置（版本化 schema + 迁移器）
├── state.db                      Deno.KV（SQLite 后端）
│                                 ├─ jobs     任务历史与快照索引
│                                 ├─ rollback 回滚点索引
│                                 ├─ probes   环境探测缓存（带 TTL）
│                                 └─ rules    诊断规则命中统计（用于优化规则）
├── audit/2026-09.ndjson          append-only 审计流（按月轮转）
├── backups/<stamp>/              备份点（含 manifest.json + sha256 清单）
├── jobs/<job_id>.json            进行中任务的 write-ahead 快照
├── logs/butler-*.log             管家自身日志（轮转）
└── report/                       体检报告导出

<DSH_ROOT>/../dsh-quarantine/<stamp>/       ← 隔离区【必须与本体同盘】
```

> **铁律继承**：隔离区**必须与 DSH 本体同盘同级**。Rust `std::fs::rename` / Python `os.rename` 跨盘必失败（winerror=17），而 Node/Deno 的 `fs.renameSync` 会自动降级成功 → **绝不能用 Node 原型验证跨盘行为**。单测 `quarantine_lives_on_the_same_volume_as_the_tree` 必须保留。

### 7.2 配置分层

| 层 | 位置 | 内容 | 谁写 |
|---|---|---|---|
| 出厂默认 | 编译进二进制 | 镜像地址（空）/ 超时阈值 / 端口候选 | 构建期 |
| 用户配置 | `~/.dsh-butler/config.json` | 路径、镜像、代理、端口、保留策略 | 用户 / 迁移器 |
| 机器本地 | `state.db` | 探测缓存、任务历史、规则统计 | 运行时 |
| 会话态 | 内存 | 当前 Job、日志缓冲、端口 | 运行时 |

**写入都是原子写**：同盘 `temp + rename`；跨盘禁止。**每次写入前先检查僵尸锁**（继承 1.18.15 的「打开管家即自愈」策略——因为用户撞上锁时服务往往已经开着，只在启动流程里清是覆盖不到真实路径的）。

### 7.3 配置 schema 版本与迁移

`config.json` 带 `schemaVersion`。启动时若低于当前版本 → 跑迁移链（逐级迁移，每级一个纯函数）→ 迁移前自动备份 `config.json.bak-<stamp>` → 写审计。**迁移永不原地覆盖**。

## 8. 备份与回滚机制

### 8.1 统一「回滚点（Rollback Point）」模型

现有项目有 3 套各自为政的备份机制（`snapshot` / `offline_pack` / `.updater_backups`）。新版统一成一种：

```ts
interface RollbackPoint {
  id: string;                      // rp-20260924T113000-a1b2
  kind: 'core-build' | 'plugin-set' | 'config' | 'snapshot' | 'env';
  createdAt: string;
  trigger: string;                 // "core.finishUpdate 前置" / 用户手动
  jobId?: string;                  // 关联任务
  artifacts: Array<{ path: string; sha256: string; size: number; mode: 'copy'|'git-ref'|'manifest-only' }>;
  reverse:                          // 逆操作配方（声明式，不存代码）
    | { op: 'restore-files' }
    | { op: 'git-reset'; commit: string; quarantine: string }
    | { op: 'npm-reinstall'; pkgJson: string; lockfile: string }
    | { op: 'rewrite-manifest'; file: string };
  verified: boolean;               // 应用后是否通过验证
  sizeBytes: number;
  expiresAt?: string;
}
```

### 8.2 生命周期

| 阶段 | 规则 |
|---|---|
| **创建** | 任何写操作**前**自动创建（write-ahead：先落盘回滚点，再动系统）。手动创建入口也保留 |
| **应用** | `backup.apply(id)` → 校验 artifacts 完整性 → 执行 reverse → 跑该域的 verify → 更新 `verified` |
| **验证** | 应用后必须验证（`core.verify` / `plugin.scan` / `runtime.health`），验证失败则**保留回滚点并告警**，不静默成功 |
| **淘汰** | 保留策略：最近 N 个（默认 10）**或**总量上限（默认 2 GB），先删最旧且已验证的；**未验证的永不自动删** |
| **恢复** | 隔离区里的东西**只移动不删除**，附带清单可整体还原（继承现有 `deep_clean` 语义） |

### 8.3 三类典型回滚

1. **本体构建回滚**：`git-reset` 到记录的 commit + 把隔离区文件移回原位 + 删除过期 `*.tsbuildinfo` + 重装依赖 + 重建（或直接恢复上一版构建产物）。
2. **插件集回滚**：恢复 `package.json` / `pnpm-lock.yaml` / `dsh.profile.bundles` 三件套 → 重装 → 复检双名单一致性。
3. **配置回滚**：直接还原 `config.json`（含 schema 版本回退）。

## 9. 失败安全策略

### 9.1 原子更新
- 文件级：同盘 `temp → fsync → rename`。**跨盘先复制再改名，绝不 rename**。
- 目录级：先完整写到 `<target>.new/` → 原子改名交换 → 旧目录移入隔离区（不删）。
- 配置级：`config.json.new` → 校验 schema → rename。
- **自更新（exe）**：下载 → SHA256 + Ed25519 双校验 → 写 `<exe>.new` → 生成 detached 替换脚本（等待当前进程退出 → 替换 → 重启）→ 替换脚本执行前先备份当前 exe 为 `<exe>.bak`。失败时脚本自动回滚到 `.bak`。

### 9.2 超时控制
- **每步独立超时**（默认：只读 10s / 网络 120s / 装依赖 15min / 构建 30min），可在配置里覆盖。
- **全局看门狗**：Job 总时长上限 + 心跳检测；超时先**收集现场**（进程树、最近日志、磁盘/内存快照）再终止，禁止无证据地杀。
- **网络请求**分层超时：连接 10s / 首字节 20s / 总时长 120s。
- 超时的 Job 保留在历史里，标记 `timeout` 并附现场，可**一键重跑**。

### 9.3 取消语义
- 取消不是"杀进程就完事"：每个步骤表都带**补偿动作**（如"已备份未安装" → 删除半成品；"已改名未交换" → 改回）。
- 取消后的状态必须与取消前**语义等价**（AC-P3 钉住）。

### 9.4 权限不足
统一四要素输出：`{ 原因, 影响, 建议动作, 一键执行入口 }`
- 例：`写 DSH 本体目录被拒（C:\Program Files\...）` → 影响"无法完成更新" → 建议"以管理员身份重启管家" → 一键"以管理员重启"。
- 检测点前置：**动手前**就探测（写测试文件 / 尝试绑定端口 / 检测提权能力），不做"干到一半才发现没权限"。

### 9.5 并发与互斥
- **单实例**：文件锁 + PID 校验（含僵尸锁自愈）。
- **域级互斥锁**：`core` / `plugin` / `runtime` 各一把；同一域的任务串行排队，跨域允许并行（但 `core.update` 会占 `runtime`，因为要停服务）。
- 排队中的任务在 UI 上可见（不是"点了没反应"）。

### 9.6 安全（因为权限必须放宽，这些是补偿措施）
| 措施 | 说明 |
|---|---|
| 本地 token | 所有 API 需 `X-Butler-Token`；只绑 `127.0.0.1` |
| 动作白名单 | 只允许注册表内的 action；参数经 schema 校验 |
| 子进程白名单 | 只允许执行 `git` / `node` / `pnpm` / `npm` / 系统只读命令；参数数组传递，**绝不过 shell 拼接** |
| 下载双校验 | SHA256 + Ed25519 签名（复用现有密钥体系，对齐官方 `{signed, signature}` 信封） |
| 危险动作二次确认 | 删除类、覆盖类、提权类必须显式 `confirm` |
| 审计全覆盖 | 所有写操作 + 提权 + 下载 落 NDJSON 审计流 |
| 脱敏 | 报告导出、日志分享前自动脱敏（用户名/路径/IP/token） |
| 路径护栏 | 禁止对系统目录、用户主目录根、盘符根做递归操作 |

### 9.7 启动自愈台账
启动时扫描并**只移动不删除**：孤儿包 / 僵尸写锁 / `*.stale-*` / `.updater_backups` 超期 / 半成品目录 / 未完成 Job。
生成一份「上次没收拾干净的东西」清单，UI 上一条提示 + 一个还原入口。

### 9.8 崩溃恢复
- 任何 Job 都要 write-ahead 落盘 `jobs/<id>.json`（步骤表 + 已完成步骤 + 当前步骤现场）。
- 下次启动检测到未完结 Job → 明确询问：**继续 / 回滚 / 仅查看现场**（三选一，不自动决定）。
- 已有回滚点的 Job 才能提供"回滚"选项；没有的只提供"继续"或"仅查看"。

## 10. 分阶段实施路线与优先级

### 10.1 优先级排序（按「用户痛感 × 风险可控 × 现有资产复用度」）

| 优先级 | 内容 | 理由 |
|---|---|---|
| **P0** | 骨架（M1/M2/M3/M13/M14/M15/M16）+ `env.probe` + `runtime.status/logs` + `diag` 只读体检 | 零风险、可独立发布、立刻可用；先把地基和"任务引擎"立起来，后面所有东西都挂在它上面 |
| **P1** | `plugin.diagnose/repair` + `runtime.diagnose/repair` + `core.status/check/verify` | 解决最高频痛点（插件加载失败、启动失败），且**只读诊断可先上、修复后上** |
| **P2** | 回滚点体系 + `core.update/finishUpdate/rollback` + `plugin` 事务安装/卸载 | 接管写操作，风险上升，但复用现有 Rust 逻辑最多 |
| **P3** | `bootstrap` 全链路 + 内嵌 DSH 窗口（★ 本次核心增量） | 价值最高，但依赖 P0–P2 的稳定性 |
| **P4** | `self.*` 自研自更新 + 跨平台构建（macOS/Linux）+ 安装包 | 收尾；Windows 上 autoUpdate 不可用，必须自研 |

### 10.2 阶段划分

| 阶段 | 交付物 | 关键验收 | 可否替换 1.18.15 |
|---|---|---|---|
| **S1 骨架 + 只读** | `2.0.0-alpha.1`：能扫环境、看服务状态、看日志、跑体检报告；Job 引擎 + 审计 + 设置 | AC-E3（三平台 probe）、AC-R4（诊断零副作用）、AC-B2 前半 | ❌ 只读，可与 1.18.15 并存 |
| **S2 诊断与修复** | `2.0.0-beta.1`：插件/运行诊断规则库（≥10 条）+ 一键修复；本体校验 | AC-P1/P2/P4、AC-R1/R2/R3、AC-C1/C4 | ❌ 还不能改本体 |
| **S3 写操作接管** | `2.0.0-rc.1`：回滚点 + 本体更新/完成更新/回滚 + 插件事务安装卸载 | AC-C2/C3、AC-P3 | ⚠️ 可切换，保留回退 |
| **S4 一键部署** | `2.0.0`：bootstrap 全链路 + 内嵌 DSH 窗口 + 托盘常驻 | AC-B1/B3/B4/B5 | ✅ 正式替代 |

### 10.3 每阶段的"不许做的事"
- S1/S2 **绝不写 DSH 目录**（除自己的 `~/.dsh-butler`）。

- 任何阶段都**不删除用户文件**，只移动进隔离区。

## 11. 主要风险与对策

| # | 风险 | 等级 | 对策 |
|---|---|---|---|
| R1 | `deno desktop` 是 experimental，API 面可能变 | 🔴 高 | ① 锁 `deno.json` 里的 Deno 版本（2.9.x）并在 CI 固定 ② 把 `deno desktop` 的能力包一层薄适配（窗口/托盘/对话框/自动更新各一个文件）③ 保留 1.18.15 作为回退 ④ 每次升级 Deno 前跑回归清单 |
| R2 | **Windows 上 `Deno.autoUpdate()` 不生效** | 🔴 高 | 自研自更新（§9.1）；不依赖官方机制；Ed25519 签名复用现有密钥 |
| R3 | 权限烘焙进二进制 → 安全边界消失 | 🟠 中高 | §9.6 的补偿措施；子进程白名单 + 参数数组传递 + 动作白名单 + 审计 |
| R4 | 失去 Rust 原生库（`winreg` / `keyring` / `sysinfo`） | 🟠 中 | `winreg` → 调 `reg.exe query` 或 Deno FFI；`sysinfo` → 系统命令（**注意 Windows 进程按命令行扫描用 CIM 很慢，必须异步 + 缓存 + 只取需要的字段**，这是现有版本踩过的性能坑）；`keyring` → 若必须，用 DPAPI/Keychain 的命令行封装或降级为"不存敏感凭据" |
| R5 | `macOS .dmg` 必须在 mac 上构建 | 🟡 中 | 第一期只出 Windows + Linux；`.dmg` 等到有 Mac 或 CI（GitHub Actions macos runner）时再做 |
| R6 | 前端从 Tauri IPC 改 HTTP，可能有行为差异（错误形态、大文件进度） | 🟡 中 | 先做完整适配层 + 契约测试；进度统一走 SSE（比 IPC 更适合流式） |
| R7 | 跨平台差异被低估（路径/换行/大小写/长路径/`.cmd` 包装） | 🟡 中 | M1 收敛 + 三平台 CI 矩阵；每平台一个冒烟测试清单 |
| R8 | `deno desktop` webview 后端 = Windows WebView2，特性比 CEF 旧 | 🟢 低 | 前端只用广泛支持的 Web 特性；若遇必须的现代 API，可切 `--backend cef`（体积换一致性，多 ~150 MB） |
| R9 | 迁移期间两套实现并存，行为不一致导致"修一半" | 🟠 中高 | 双跑期只读对比（同输入 → 比结论）；写操作**只有一个实现有权执行**（用互斥锁文件 + 版本栅栏） |
| R10 | 诊断规则库变成"猜谜大全"（误报/漏报） | 🟡 中 | 每条规则必须有阳性+阴性样本；命中率进 `state.db` 统计；误报可一键上报 |
| R11 | 一次性重构工程量被低估 | 🟠 中高 | 严格分阶段；S1/S2 就能交付可感知价值；**不追求一次替换** |

## 12. 旧项目数据与配置的迁移思路

### 12.1 不变量（绝对不能动）
| 项 | 值 | 原因 |
|---|---|---|
| 应用 identifier | `com.dsh.plugin-updater` | 改了 = 挪数据目录、丢配置、**断掉自更新链**（`deno.json` 的 `desktop.app.identifier` 必须照写） |
| 自更新清单契约 | `version.json` 顶层 `sha256` / `size_bytes` | 客户端只读顶层，不读 `platforms.*` |
| DSH 目录布局 | `~/.dsh/**` 不做重命名 | 用户数据 + 旧版兼容 |
| 双名单逻辑 | `activePlugins = dependencies ∩ dsh.profile.bundles` | 改错就"装了不生效"或"卸载后启动即崩" |
| 隔离区同盘约束 | `<DSH_ROOT>/../dsh-quarantine/` | 跨盘必失败 |

### 12.2 配置迁移

```
~/.dsh/plugin-updater-config.json   （旧）
        │  迁移器（只读旧文件，绝不删改）
        ▼
~/.dsh-butler/config.json           （新，schemaVersion: 1）
        + audit 记录一次 migration
        + 旧文件原地保留（备份 `plugin-updater-config.json.migrated.bak`）
```

字段映射：`dsh_mirror_url` / `proxy_base_url` / 端口 / 目录 → 同名或改名后写入；新增字段给默认值；**已废弃字段（服务器同步相关）不再迁移**（现有版本已把默认值清空，属于有意淘汰）。

其他要识别并复用的旧数据：
- `~/.dsh/web-dir`（DSH 根路径缓存）→ 直接读，迁移为新配置的 `dshRoot` 初值
- `~/.dsh/profiles/web/.updater_backups/**`（旧备份）→ 注册为"历史遗留备份"，在 UI 上可见、可还原、可清理；**首版不改动它们**
- `~/.dsh/profiles/web/package.json.bak*`（多份）→ 同上，纳入"残留物台账"
- `~/.dsh/dsh-mcp.json*` → `mcp.*` 模块继续读写原路径

### 12.3 迁移步骤（可回退）

```
1. 迁移前：自动创建回滚点（含 ~/.dsh 下所有相关配置 + profile 清单的哈希）
2. 只读扫描：列出"将被迁移 / 将不被识别 / 有冲突"三类清单 → 给用户看
3. 用户确认 → 写新配置（新目录）→ 旧文件原地保留
4. 复检：新配置解析成功 + 关键字段与原值一致 → 写审计
5. 失败：一键还原（删除新目录即可，旧文件从未被改动）
```

**原则：迁移过程对旧数据是"只读"的。** 新目录可以随便删，删了就回到迁移前。

### 12.4 与 1.18.15 的并存与切换

| 阶段 | 策略 |
|---|---|
| S1–S2 | Deno 版**只读**，与 1.18.15 并存；提供"对比模式"：两个版本对同一状态各出一份结论，人工核对是否一致 |
| S3 | Deno 版接管写操作，1.18.15 保留为回退；两版共享同一互斥锁文件，**同一时刻只有一个能执行写操作** |
| S4+ | 正式替代；1.18.15 从官网下架但保留安装包（`安装包/` 目录已有历史产物） |

### 12.5 发布链路迁移

| 现有 | 新方案 |
|---|---|
| `scripts/build-release.ps1`（Rust `--remap-path-prefix` 剥路径） | **不再需要**（Deno 编译不嵌入构建机 cargo 路径）——但需实测确认产物里不含用户名/绝对路径，保留一个自检脚本 |
| `tauri build --bundles nsis` + 手工 MSI 补丁 | `deno desktop` 一行直出 `.msi`（LGHT0311 那个坑直接消失） |
| `self_update`（下载 exe + 替换） | 逻辑移植到 M9（TS 版），契约不变 |
| `version.json` + Ed25519 验签 | 保留；可选升级为官方 `{signed, signature}` 信封，与 `Deno.autoUpdate` 兼容（为将来 Windows 支持做准备） |
| 裸 exe 上传（≈19.7 MB） | `.msi` + `.exe` 双产物上传；`version.json` 结构兼容 |

### C. 前端适配层（Tauri → HTTP，一个文件）

```ts
// src-vue/src/api/transport.ts
const TOKEN = new URLSearchParams(location.search).get("t") ?? "";
export async function invoke(action: string, params: unknown = {}) {
  const r = await fetch("/api/jobs", {
    method: "POST",
    headers: { "content-type": "application/json", "x-butler-token": TOKEN },
    body: JSON.stringify({ action, params }),
  });
  if (!r.ok) throw new Error(await r.text());
  const { jobId } = await r.json();
  return await waitForJob(jobId);     // SSE 订阅，兼容旧的 Promise 语义
}
```
