## 1. 项目概述

### 1.1 项目背景

DSH 插件升级管理工具是一个**独立运行**的桌面应用程序，用于管理 DSH Agent 生态系统中的所有插件。工具不依赖 Agent 本体进程，通过文件系统操作和代理服务实现插件的扫描、更新、启停、卸载等全生命周期管理。

### 1.2 项目目标

| 目标 | 描述 | 验收标准 |
|------|------|----------|
| 独立性 | 不依赖 Agent 本体运行 | 关闭 Agent 后工具仍可正常扫描和管理 |
| 稳定性 | 操作流程稳定可靠 | 连续操作 100 次无崩溃，错误率 < 0.1% |
| 速度 | 访问速度快 | 插件更新检测 < 5秒/个，下载速度 > 1MB/s |
| 易用性 | 界面友好 | 新用户 3 分钟内可完成首次插件更新 |
| 安全性 | 数据和操作安全 | 无数据泄露，更新失败可回滚，卸载可恢复 |

### 1.3 项目范围

**包含：**
- 桌面客户端（Windows / Linux）
- 代理服务
- 官方网站（含插件市场、下载、文档）
- 插件清单规范

**不包含：**
- Agent 本体开发
- 插件本身的开发
- 移动端应用

## 4. 接口设计规范

### 4.1 网络代理 API

#### 4.1.1 获取最新 Release

```
GET /api/github/latest?repo={owner/repo}
```

**请求参数：**

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| repo | string | 是 | GitHub 仓库，格式 owner/repo |

**请求头：**

| 头部 | 类型 | 必填 | 说明 |
|------|------|------|------|
| X-Proxy-Token | string | 否 | 代理访问令牌（配置后必填） |

**响应示例：**

```json
{
  "tag_name": "v1.2.0",
  "name": "Release v1.2.0",
  "html_url": "https://github.com/owner/repo/releases/tag/v1.2.0",
  "body": "## 更新内容\n- 修复了...\n- 新增了...",
  "assets": [
    {
      "name": "plugin-v1.2.0.zip",
      "browser_download_url": "https://github.com/.../plugin-v1.2.0.zip",
      "size": 1048576,
      "content_type": "application/zip"
    }
  ],
  "published_at": "2026-08-28T00:00:00Z"
}
```

**错误响应：**

```json
{
  "error": "GitHub API error: rate limit exceeded"
}
```

#### 4.1.2 下载 Release 资产

```
GET /api/github/download?repo={owner/repo}&tag={tag}&asset={filename}
```

**响应：** 文件流（Content-Disposition: attachment）

## 5. 开发规范

### 5.1 代码规范

#### 5.1.1 Rust 代码规范

- 使用 `cargo fmt` 格式化代码
- 使用 `cargo clippy` 进行代码检查
- 错误处理统一使用 `AppError` 枚举，禁止 `unwrap()` 生产代码
- 异步函数必须标记 `#[tauri::command]`
- 文件操作必须考虑跨平台兼容性
- 日志使用 `log` crate，分级输出

#### 5.1.2 TypeScript/Vue 代码规范

- 使用 Composition API + `<script setup lang="ts">`
- 组件命名使用 PascalCase
- Props 必须定义类型和默认值
- 状态管理统一使用 Pinia
- API 调用统一封装在 `api/` 目录
- 禁止使用 `any` 类型，必须定义明确的接口

#### 5.1.3 Go 代码规范

- 使用 `gofmt` 格式化代码
- 使用 `go vet` 进行代码检查
- 错误处理必须检查，禁止忽略错误
- 公共函数必须有注释
- HTTP 处理函数必须设置超时
- 数据库/缓存操作必须有连接池配置

### 5.2 Git 工作流

#### 5.2.1 分支策略

| 分支 | 用途 | 命名规范 |
|------|------|----------|
| `main` | 主分支，生产代码 | - |
| `develop` | 开发分支 | - |
| `feature/*` | 功能开发 | `feature/plugin-auto-update` |
| `fix/*` | Bug 修复 | `fix/update-crash-on-windows` |
| `release/*` | 发布准备 | `release/v1.1.0` |
| `hotfix/*` | 紧急修复 | `hotfix/security-patch` |

#### 5.2.2 提交信息规范

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Type 类型：**

| 类型 | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 文档更新 |
| `style` | 代码格式（不影响功能） |
| `refactor` | 重构 |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `chore` | 构建/工具/依赖 |
| `security` | 安全修复 |

**示例：**
```
feat(updater): add incremental update support

- support delta updates to reduce download size
- add checksum verification for update packages
- add progress callback for download status

Closes #123
```

### 5.3 版本管理

- 遵循语义化版本（SemVer）：`MAJOR.MINOR.PATCH`
- 版本号同步更新：`Cargo.toml`, `tauri.conf.json`, `package.json`, `go.mod`
- 每个版本必须更新 `CHANGELOG.md`
- 发布前必须通过全部测试和安全扫描

### 7.2 代理服务部署

#### 7.2.1 Docker Compose 部署

```yaml
version: '3.8'
services:
  proxy:
    build: .
    restart: unless-stopped

      - "8080:8080"
    environment:
      - GITHUB_TOKEN=${GITHUB_TOKEN}

      - redis
    healthcheck:

      timeout: 10s

    restart: unless-stopped
    command: redis-server --appendonly yes --maxmemory 256mb
    volumes:
      - redis-data:/data
```

#### 7.2.2 Nginx 反向代理配置

```nginx
server {
    listen 443 ssl http2;
    server_name proxy.dsh.huilinsh.cn;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    # 限流
    limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;

    location / {
        limit_req zone=api_limit burst=20 nodelay;
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 300s;
        client_max_body_size 500M;
    }
}
```

| 指标 | 告警阈值 | 告警级别 |
|------|----------|----------|
| 服务可用性 | < 99.9% | P0 |
| API 响应时间 (P95) | > 2s | P1 |
| API 错误率 | > 5% | P1 |
| Redis 内存使用 | > 80% | P2 |
| 磁盘使用 | > 85% | P2 |
| CPU 使用率 | > 80% 持续5分钟 | P2 |
| GitHub API 限流 | 剩余 < 100 | P1 |

#### 7.3.2 日志规范

- 所有请求必须记录：时间、方法、路径、状态码、耗时、客户端IP
- 错误日志必须包含：错误信息、堆栈跟踪、请求上下文
- 日志保留：生产环境 30 天，测试环境 7 天
- 日志轮转：单文件最大 100MB，保留 10 个备份

### 7.4 备份策略

| 数据 | 备份频率 | 保留时间 | 存储位置 |

## 8. 风险控制体系

### 8.1 风险分类与评估矩阵

#### 8.1.1 风险等级定义

| 等级 | 概率 | 影响 | 风险值 | 响应时间 |
|------|------|------|--------|----------|
| P0 极高 | > 50% | 服务中断/数据丢失 | > 15 | 立即（< 15分钟） |
| P1 高 | 30%-50% | 功能受损/性能严重下降 | 10-15 | 1小时内 |
| P2 中 | 10%-30% | 部分功能异常/体验下降 | 5-10 | 24小时内 |
| P3 低 | < 10% | 轻微影响/可绕过 | < 5 | 下个版本修复 |

**风险值 = 概率分(1-5) × 影响分(1-5)**

#### 8.1.2 风险评估矩阵

```
影响
 5 │  P0   P0   P1   P1   P2
 4 │  P0   P1   P1   P2   P2
 3 │  P1   P1   P2   P2   P3
 2 │  P1   P2   P2   P3   P3
 1 │  P2   P2   P3   P3   P3
   └──────────────────────────
     1    2    3    4    5  概率
```

### 8.2 技术风险

## 9. 应急预案

### 9.1 应急响应流程

```
发现事件 → 初步评估（< 15分钟）→ 启动应急预案
    → 执行应急措施 → 监控恢复情况 → 事件复盘
    → 更新风险登记册 → 改进预防措施
```

### 9.2 典型场景应急预案

#### 9.2.1 代理服务完全不可用

**触发条件：** 健康检查连续失败 3 次，或用户集中反馈无法检查更新

**应急措施：**

1. **立即（0-15分钟）**
   - 通知所有相关人员
   - 检查服务器状态（CPU/内存/磁盘/网络）
   - 检查 Docker 容器状态，尝试重启服务
   - 在官网和客户端发布公告

2. **短期（15-60分钟）**
   - 如果服务器故障，切换到备用节点
   - 如果是 GitHub 问题，等待 GitHub 恢复，缓存已有数据
   - 临时提高 Redis 缓存时间，减少对 GitHub 的请求
   - 客户端降级：显示缓存的版本信息，提示"更新检测暂时不可用"

3. **长期（> 1小时）**
   - 多节点部署，负载均衡
   - 考虑使用其他 Git 平台作为备用源（Gitee/GitLab）
   - 客户端支持配置多个代理地址，自动切换

**回滚验证：** 健康检查恢复正常，用户可正常检查更新，监控指标恢复正常

#### 9.2.2 插件更新失败导致插件损坏

**触发条件：** 用户反馈更新后插件无法使用，或更新过程中报错

**应急措施：**

1. **立即（0-15分钟）**
   - 指导用户从备份恢复（工具内置恢复功能）
   - 收集错误日志和插件信息
   - 暂停该插件的更新推送（在代理服务端标记）

2. **短期（15-60分钟）**
   - 定位失败原因（网络问题/包损坏/兼容性问题）
   - 如果是更新包问题，重新发布正确的版本
   - 如果是兼容性问题，添加版本兼容检查，阻止不兼容的更新
   - 更新 FAQ 和故障排除文档

3. **长期（> 1小时）**
   - 完善更新前校验机制（校验和、兼容性检查、磁盘空间检查）
   - 增加更新失败自动回滚功能（当前需要手动恢复）
   - 建立插件测试环境，更新发布前在多环境测试

**回滚验证：** 用户可成功恢复插件，新版本更新包验证通过，无新增失败报告

#### 9.2.3 安全漏洞被利用

**触发条件：** 安全监控发现异常行为，或收到安全研究者报告

**应急措施：**

1. **立即（0-15分钟）**
   - 评估漏洞影响范围和严重程度
   - 如果是代理服务漏洞，立即关闭受影响的接口或服务
   - 如果是客户端漏洞，发布紧急安全公告
   - 通知安全团队介入

2. **短期（15-60分钟）**
   - 开发修复补丁
   - 代理服务：热修复部署，不需要重启
   - 客户端：发布紧急修复版本，强制更新提示
   - 检查是否已有被利用的痕迹，清理受影响数据

3. **长期（> 1小时）**
   - 完整的安全审计，排查类似漏洞
   - 加强安全测试和代码审查
   - 建立漏洞赏金计划，鼓励安全研究者报告
   - 定期进行渗透测试

**回滚验证：** 漏洞修复验证通过，安全监控无异常，发布安全公告说明修复情况

#### 9.2.4 数据丢失（插件目录被误删）

**触发条件：** 用户反馈插件目录全部丢失，或工具操作导致目录删除

**应急措施：**

1. **立即（0-15分钟）**
   - 停止所有文件操作，防止数据覆盖
   - 检查备份目录是否存在
   - 指导用户从备份恢复

2. **短期（15-60分钟）**
   - 如果备份不存在，使用数据恢复软件尝试恢复
   - 检查是否有系统还原点（Windows）
   - 收集操作日志，定位删除原因

3. **长期（> 1小时）**
   - 加强删除操作的安全机制（更多确认、更严格的路径校验）
   - 自动备份机制优化（备份到不同位置、云端备份选项）
   - 删除操作增加回收站功能（软删除，可恢复）

**回滚验证：** 用户数据成功恢复，删除操作安全机制验证通过
